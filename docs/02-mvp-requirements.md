# MVP 需求规格

> 文档状态：MVP 基线 + Phase 5 已批准范围
> 优先级说明：P0 = 当前阶段必须；P1 = 后续增强；P2 = 远期候选
> 需求编号是设计、实现、测试和变更记录的共同引用键

## 1. 范围摘要

MVP 面向单一用户，以本地优先 Web/PWA 形式提供快速收集、每日计划、任务组织、搜索和数据备份能力。MVP 基线不依赖账号、服务器和第三方服务。Phase 5 在此基线上增加可选登录和私有云同步；未登录时仍可使用本地能力。

## 2. 功能需求

### MVP-001 快速创建任务（P0）

用户故事：作为用户，我希望只输入标题并确认就创建任务，以免记录过程打断当前工作。

验收条件：

- Inbox、Today 等主要页面均有快速创建入口。
- 标题去除首尾空格后不能为空。
- 按 Enter 或点击创建后，新任务立即出现。
- 快速创建默认写入 Inbox；在 Today 页面创建时同时将 `plannedDate` 设为今天。
- 连续提交不会意外生成重复任务。
- 创建成功后输入框清空并继续保持可输入状态。

### MVP-002 查看与编辑任务详情（P0）

用户故事：作为用户，我希望在记录后补充任务信息，以便先收集、后整理。

可编辑字段：标题、备注、重要性、紧急性、计划日期、截止日期、项目、标签。

验收条件：

- 标题仍不能为空。
- `plannedDate` 与 `deadline` 分别标注为“计划日期”和“截止日期”。
- 保存后所有相关视图同步更新。
- 取消编辑不会写入未保存内容。
- 关闭详情后再次打开，显示最新持久化数据。

### MVP-003 完成与恢复任务（P0）

用户故事：作为用户，我希望快速完成任务，并能恢复误完成的任务。

验收条件：

- 列表中可一键完成任务。
- 完成时记录 `completedAt`。
- 完成任务从活动视图移除并出现在 Completed。
- 操作后提供短时撤销入口。
- 在 Completed 中可以恢复，恢复后清空 `completedAt` 并重新进入对应活动视图。

### MVP-004 删除、撤销与软删除（P0）

用户故事：作为用户，我希望删除无用任务，并能撤销误删。

验收条件：

- 删除后任务立即从普通视图消失。
- 删除以 `deletedAt` 软删除实现。
- 删除后提供短时撤销。
- 已删除任务不出现在搜索、计数和导出之外的普通视图中。
- MVP 不提供独立回收站页面；永久清理属于后续能力。

### MVP-005 Inbox 收集箱（P0）

用户故事：作为用户，我希望先收集未整理任务，再在合适时间处理。

验收条件：

- 快速创建默认 `inbox = true`。
- 用户为任务安排计划日期或项目后，系统默认将其视为已整理并设为 `inbox = false`。
- 用户可以在详情中手动移回 Inbox。
- Inbox 只显示未删除、未完成且 `inbox = true` 的任务。

### MVP-006 Today 每日计划（P0）

用户故事：作为用户，我希望区分今天主动计划的任务和今天必须完成的任务。

Today 至少包含以下分组：

1. 逾期截止：`deadline < today`。
2. 今日截止：`deadline = today`。
3. 未完成结转：`plannedDate < today` 且仍未完成。
4. 今日计划：`plannedDate = today`。

验收条件：

- 同一任务只显示一次，按最高紧迫分组归属。
- 逾期截止有明显但不过度刺眼的视觉提示。
- 用户可以将任务加入今天、移出今天或改到其他日期。
- 只移出今日计划时不得清除任务的 `deadline`。
- 日期计算使用用户本地时区和自然日边界。

### MVP-007 Upcoming 即将到来（P0）

用户故事：作为用户，我希望看到未来安排和截止压力，以便提前调整计划。

验收条件：

- 展示未来 7 天内存在 `plannedDate` 或 `deadline` 的活动任务。
- 按自然日分组。
- 同一任务同一天只显示一次，同时展示计划/截止标识。
- 如果计划日期和截止日期不同，只在两者中较早的相关日期显示一次，并继续展示另一个日期作为元信息。
- 可以从该视图修改计划日期和截止日期。
- “未来 7 天”不包含今天；今天由 Today 展示。

### MVP-008 项目与标签（P0）

用户故事：作为用户，我希望用项目表达归属，用标签表达跨项目场景。

验收条件：

- 用户可以创建、重命名和归档项目。
- 一项任务最多属于一个项目，也可以不属于任何项目。
- 用户可以创建、重命名和删除标签。
- 一项任务可以拥有多个标签。
- 项目和标签视图只查询任务，不复制任务。
- 删除正在使用的标签前必须展示影响数量并确认；确认后仅移除关联，不删除任务。
- 归档项目后项目不出现在默认创建选项中，原任务仍可访问。

### MVP-009 搜索、筛选与排序（P0）

用户故事：作为用户，我希望快速找到特定任务和当前需要关注的任务。

验收条件：

- 搜索标题和备注，忽略大小写并匹配包含关系。
- 默认不搜索已删除任务。
- 可以选择是否包含已完成任务。
- 支持按状态、重要性、紧急性、四象限、未分类、项目、标签进行基础筛选。
- 重要性筛选与紧急性筛选可以组合，组合时采用 AND 语义。
- 支持按计划日期、截止日期、四象限和创建时间排序。
- 清除条件后恢复当前页面的默认视图。

### MVP-010 本地持久化与离线使用（P0）

用户故事：作为用户，我希望没有账号和网络也能使用核心功能。

验收条件：

- 任务、项目、标签和设置保存在 IndexedDB。
- 页面刷新和浏览器重启后数据仍存在。
- 应用加载过一次后，离线状态可以打开应用壳并完成核心任务操作。
- 数据写入失败时明确提示，不得假装保存成功。
- 数据库迁移失败时停止写入并给出恢复提示。

### MVP-011 数据导出与恢复（P0）

用户故事：作为用户，我希望随时取得完整数据副本，并能从备份恢复。

验收条件：

- 导出为 UTF-8 JSON 文件。
- 文件包含 `schemaVersion`、`exportedAt`、应用版本和完整业务数据。
- 导入前校验结构、版本、必填字段和引用关系。
- MVP 导入模式为“替换恢复”，必须展示数据摘要并二次确认。
- 导入在单个事务中完成；任何错误都不得留下部分导入数据。
- 导入成功后刷新全部视图并显示恢复数量。

### MVP-012 响应式、键盘与无障碍基础（P0）

用户故事：作为用户，我希望在桌面和手机上顺畅使用，并能用键盘完成高频操作。

验收条件：

- 360px 宽度下无阻断性横向滚动。
- 桌面支持 `/` 聚焦搜索、`n` 聚焦快速创建、`Esc` 关闭详情或取消编辑。
- 所有图标按钮有可访问名称。
- 主要交互可通过键盘访问，并有可见焦点。
- 状态变化不只依赖颜色表达。
- 触控目标尺寸满足常见移动端可用性要求。

### MVP-013 PWA 与应用状态（P0）

用户故事：作为用户，我希望把工具作为独立应用打开，并清楚知道当前是否离线。

验收条件：

- 提供有效的 Web App Manifest。
- 核心静态资源可被 Service Worker 缓存。
- 离线时展示非阻断提示，不影响本地操作。
- 新版本可用时提示刷新，不在用户编辑过程中强制刷新。

### MVP-014 重要性与紧急性分类（P0）

用户故事：作为用户，我希望分别判断任务是否重要、是否紧急，并根据判断结果筛选任务，以便决定关注顺序。

数据语义：

- 重要性：未设置 / 重要 / 不重要。
- 紧急性：未设置 / 紧急 / 不紧急。
- 两个维度相互独立，各自内部互斥。
- 快速创建默认两个维度均为“未设置”，不增加创建阻力。

四象限组合：

1. 重要且紧急：`importance = important` 且 `urgency = urgent`。
2. 重要但不紧急：`importance = important` 且 `urgency = not-urgent`。
3. 不重要但紧急：`importance = not-important` 且 `urgency = urgent`。
4. 不重要且不紧急：`importance = not-important` 且 `urgency = not-urgent`。

验收条件：

- 任务详情使用两个独立的单选/分段控件设置重要性和紧急性。
- UI 可以将已设置值显示为“重要”“不重要”“紧急”“不紧急”的系统分类标识。
- 系统不允许同一任务同时处于“重要”和“不重要”，或同时处于“紧急”和“不紧急”。
- 用户可以清除任一维度，使其恢复为“未设置”。
- 用户可以筛选所有重要任务，而不限制其紧急性；反向亦然。
- 用户可以直接筛选四个完整象限。
- 任一维度未设置的任务可通过“未分类”筛选找到，不属于任何完整象限。
- 系统分类标识与用户自定义 Tag 分开存储、分开展示；重命名或删除普通标签不影响重要性/紧急性。
- MVP 只提供分类标识、筛选和排序，不增加独立四象限矩阵页面。

## 3. 非功能需求

### NFR-001 性能

- 在 5,000 条任务规模下，常用列表滚动和搜索保持可用。
- 本地查询不得在每次按键时扫描无关大对象或阻塞主线程。
- 常用页面首次可交互目标为普通设备和稳定网络下 2 秒以内；离线缓存命中应更快。

### NFR-002 可靠性

- 所有多表写入使用事务。
- 更新时间戳由单一领域服务生成。
- 导入、迁移和批量操作失败时保持原有数据一致。

### NFR-003 隐私

- MVP 基线不向服务器上传任务内容；Phase 5 只有在用户登录、明确启用同步并确认首次迁移后才上传。
- 不引入记录任务标题、备注或搜索词的分析服务。
- 服务端日志、错误监控和遥测不得记录任务标题、备注、搜索词或完整同步负载。
- 若未来增加业务遥测，必须默认不包含任务内容并单独记录决策。

### NFR-004 安全

- 备注按纯文本处理，渲染时不得执行 HTML。
- 导入文件有大小上限和结构校验。
- Service Worker 不缓存用户导出的数据文件。

### NFR-005 可维护性

- UI 不直接操作 Dexie 表；通过 Repository/Service 访问数据。
- 日期分组、Today 归属、四象限派生和导入校验必须是可单元测试的纯逻辑。
- 数据模型变更必须增加 schema migration 并更新本文件、数据模型和验收测试。

### NFR-006 兼容性

- 支持当前主流 Chromium、Safari 和 Firefox 的现代版本。
- 不承诺旧版浏览器或无 IndexedDB 环境。

### NFR-007 可观测性

- 开发环境记录结构化错误。
- 生产环境向用户展示可理解的错误消息，不显示堆栈、数据库细节或敏感内容。

## 4. Phase 5 私有云同步需求

Phase 5 是独立于 MVP 发布基线的范围增量。以下 P0 指“Phase 5 发布必须”，不改变 MVP-001～MVP-014 已有验收结论。

### SYNC-001 可选登录与本地模式（P0）

用户故事：作为个人用户，我希望无账号时仍能使用本地待办，在需要跨设备时再登录启用同步。

验收条件：

- 未登录时，MVP 的创建、编辑、完成、查询、离线和 JSON 备份能力继续可用。
- 登录成功不自动上传既有本地数据；先展示同步说明和本地数据摘要。
- 云同步只允许一个账号访问自己的数据，产品不提供团队、成员或共享空间。
- 登录失效时停止云端请求并提示重新登录，不影响已经成功写入 IndexedDB 的本地操作。
- 退出登录默认停止同步但不静默删除本地数据；清除此设备数据必须是独立的高风险操作并二次确认。

### SYNC-002 云端持久化与用户隔离（P0）

用户故事：作为已启用同步的用户，我希望任务保存在受保护的云数据库中，并且只有我能访问。

验收条件：

- 任务、项目、标签和设置同步到托管 PostgreSQL。
- 浏览器不持有数据库连接串或服务端密钥，只通过受鉴权的 HTTPS API 访问云端数据。
- 服务端从已验证会话推导 `userId`，不得信任客户端提交的所有者字段。
- 所有读取、写入、删除和首次迁移都按 `userId` 隔离。
- 未认证、会话过期或跨用户资源请求返回明确错误，且不泄露资源是否存在。
- 云端写入失败时客户端不得显示“已同步”。

### SYNC-003 本地优先的离线同步（P0）

用户故事：作为已启用同步的用户，我希望断网时照常使用，联网后修改自动补传。

验收条件：

- 用户操作先在一个 IndexedDB 事务中更新本地业务数据并写入待同步队列，界面立即响应。
- 在线且会话有效时，客户端按队列顺序或等价的因果安全方式向服务端提交修改。
- 每个修改具有稳定的 `mutationId`；重复提交不得产生重复实体或重复副作用。
- 网络中断、超时和可重试服务端错误保留队列并使用有上限的退避重试。
- 应用恢复网络、重新获得有效会话或重新打开时会继续未完成同步。
- 同步状态至少区分：仅本地、同步中、已同步、离线待同步、同步失败、存在冲突。

### SYNC-004 增量拉取、删除与冲突保护（P0）

用户故事：作为在多个设备修改任务的用户，我希望最终看到一致结果，并且并发修改不会被静默覆盖。

验收条件：

- 客户端通过服务端游标增量拉取变更，而不是每次覆盖整库。
- 每个云端实体具有单调递增的 `revision`；写入携带客户端已知的 `baseRevision`。
- `baseRevision` 过期时服务端拒绝覆盖并返回当前云端版本。
- 客户端保留本地版本和云端版本，展示冲突并允许用户明确选择；解决前不得把任一版本静默丢弃。
- 删除以墓碑同步；其他设备拉取后删除对应本地活动实体，且离线设备不能因旧快照使其复活。
- 同一同步批次中的引用修改在服务端事务中校验和提交。

### SYNC-005 既有本地数据首次迁移（P0）

用户故事：作为已经使用本地版的用户，我希望启用同步时安全上传现有数据，不丢失、不重复。

验收条件：

- 迁移前展示任务、项目、标签数量并建议先导出 JSON 备份。
- 只有云端账户为空时允许自动首次上传；本地与云端同时非空时停止自动迁移并提示用户处理，不擅自合并或覆盖。
- 用户确认后，以可重试且幂等的批次上传当前本地快照。
- 迁移失败或取消时，原 IndexedDB 数据保持不变，用户可重试或继续仅本地使用。
- 服务端确认完整快照后才标记迁移成功并开始正常增量同步。
- 第二台空设备登录后应从云端拉取，不触发反向空库覆盖。

### SYNC-006 同步状态、恢复与备份共存（P0）

用户故事：作为用户，我希望知道数据当前保存在哪里、上次何时同步，并能在出错时恢复。

验收条件：

- Settings 展示账号、同步开关/状态、待同步数量、冲突数量、上次成功同步时间和重试入口。
- 全局状态只在需要时提示离线待同步、持续失败或冲突，不用频繁成功 Toast 打扰用户。
- 用户可暂停同步；暂停不删除本地或云端数据。
- JSON 导出与事务性恢复继续可用，并明确说明本地备份与云同步不是同一件事。
- 从 JSON 恢复到已启用同步的设备前必须暂停同步；恢复后将其作为一批明确确认的新变更上传，不直接覆盖云端。
- 清除设备本地数据前检查未同步修改并给出阻断或明确风险提示。

### NFR-SYNC-001 安全与隐私（P0）

- 全部同步 API 使用 HTTPS、服务端鉴权、输入 schema 校验和请求体大小限制。
- 生产环境数据库凭据仅存在于服务端环境变量；不得使用 `VITE_` 等会被打入浏览器包的前缀。
- 服务端查询必须包含用户边界；关键隔离规则需要集成测试。
- 日志仅记录请求 ID、用户的不可逆匿名标识、实体类型、数量、错误码和耗时，不记录任务内容。
- 登录令牌过期、撤销和重放风险必须按所选身份提供商的官方服务端验证方式处理。

### NFR-SYNC-002 一致性与可恢复性（P0）

- 推送批次、首次迁移和涉及多表引用的写入使用数据库事务。
- 同一 `mutationId` 在同一用户范围内只执行一次。
- 同步协议、云端 schema 和本地同步表都必须版本化并具备迁移测试。
- 客户端异常关闭后，已提交的本地数据和待同步队列仍可恢复。
- 云端故障不得阻断本地创建和编辑；同步失败不得导致队列或冲突记录丢失。

## 5. P1 候选需求

- P1-001 子任务/检查清单。
- P1-002 拖拽排序。
- P1-003 自然语言日期识别。
- P1-004 周期任务。
- P1-005 浏览器或系统提醒。
- P1-006 日历视图。
- P1-007 自定义智能列表。
- P1-008 回收站和永久删除。

P1 不得在 P0 验收完成前插入开发，除非记录明确的范围变更决策。

## 6. 需求完成定义

一项 P0 需求只有同时满足以下条件才算完成：

1. 对应交互已实现。
2. 对应数据规则已实现并持久化。
3. 需求涉及的异常和空状态已处理。
4. 自动化测试或指定人工验收已通过。
5. 不破坏其他 P0 场景。
6. 文档与实现保持一致。

Phase 5 的 `SYNC-*` 需求还必须满足：云端迁移已在隔离环境演练；用户隔离、幂等、离线重试、删除墓碑和冲突场景通过；生产凭据未进入客户端构建产物。
