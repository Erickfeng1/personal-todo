## D-001 MVP 采用响应式 Web/PWA

- 状态：Accepted
- 日期：2026-08-11
- 背景：产品需要低成本覆盖桌面和手机，并适合 Vibe Coding 小步迭代。
- 决策：第一版做响应式 Web 应用，并提供 PWA Manifest、离线应用壳和可安装能力。
- 理由：一套代码覆盖主要设备；不需要应用商店发布；适合静态部署。
- 代价：系统级提醒、快捷入口和后台能力弱于原生 App；Safari 本地存储策略需要额外验证。
- 后续触发：真实使用证明系统级通知或原生入口是核心需求时，再评估原生封装或 App。

## D-002 本地优先、无需登录

- 状态：Accepted
- 日期：2026-08-11
- 背景：单人个人工具的首要价值是打开即用和数据控制，而不是协作。
- 决策：MVP 数据保存在 IndexedDB；无需账号；不上传任务内容。
- 理由：降低开发复杂度和使用门槛，天然支持离线。
- 代价：清除浏览器站点数据可能造成丢失；MVP 无多设备同步。
- 缓解：导出恢复进入 P0；设置页明确风险。
- 后续触发：连续使用后出现稳定的跨设备需求，再设计可选同步，而不是直接把本地表暴露给云端。

## D-003 分离计划日期与截止日期

- 状态：Accepted
- 日期：2026-08-11
- 背景：竞品研究显示“今天准备做”与“今天到期”是不同心智模型。单一日期字段会导致 Today 混乱。
- 决策：Task 同时支持 `plannedDate` 和 `deadline`。
- 理由：用户可以今天开始处理、周五完成；移出 Today 不会丢失硬期限。
- 代价：详情页多一个字段，Today 分组和 Upcoming 查询更复杂。
- 缓解：使用明确文案和渐进式呈现。

## D-004 一个项目、多个标签

- 状态：Accepted
- 日期：2026-08-11
- 背景：项目表达主要归属，标签表达跨项目情境。
- 决策：Task 的 `projectId` 为单值可空，`tagIds` 为多值。
- 理由：心智模型清楚，满足“工作项目 + 等待回复标签”等场景。
- 代价：标签删除需要事务性清理关联。
- 被拒绝方案：允许一项任务属于多个项目；这会增加归属、排序和完成统计歧义。

## D-005 Today 等页面为派生视图

- 状态：Accepted
- 日期：2026-08-11
- 背景：任务可能同时符合 Today、项目、标签和搜索条件。
- 决策：所有视图从同一 Task 数据查询，不复制任务。
- 理由：避免状态不一致和重复完成。
- 代价：查询和去重规则必须集中实现和测试。

## D-006 完成可恢复、删除采用软删除

- 状态：Accepted
- 日期：2026-08-11
- 背景：完成和删除都是高频误操作来源。
- 决策：完成记录 `completedAt` 并可恢复；删除设置 `deletedAt` 并提供短时撤销。
- 理由：比每次弹确认框更流畅，同时降低不可逆风险。
- 代价：普通查询都要默认排除软删除数据。
- 备注：MVP 不提供回收站和永久清理。

## D-007 MVP 导入仅支持替换恢复

- 状态：Accepted
- 日期：2026-08-11
- 背景：合并导入涉及重复 ID、引用冲突、时间戳和用户选择，显著扩大范围。
- 决策：MVP 只支持完整导出和事务性“替换恢复”。
- 理由：优先保证备份可验证和恢复可靠。
- 代价：用户不能把两份独立数据库自动合并。
- 缓解：恢复前展示摘要并建议先导出当前数据。

## D-008 MVP 不做自然语言、周期和提醒

- 状态：Accepted
- 日期：2026-08-11
- 背景：自然语言、周期和提醒都有高用户价值，但各自存在明显边界复杂度。
- 决策：MVP 使用显式日期选择；不实现周期任务和通知，也不自动判断重要性或紧急性。
- 理由：先验证收集、Today 和数据安全闭环。
- 代价：创建速度和重复任务体验不如成熟竞品。
- 后续触发：真实使用一周后，以频率和痛点排序进入 P1。

## D-009 UI 不直接操作数据库

- 状态：Accepted
- 日期：2026-08-11
- 背景：若组件直接依赖 Dexie，规则会分散，未来同步或迁移成本高。
- 决策：组件通过 Application Service、Repository 和 Query Hook 访问数据。
- 理由：集中业务不变量、错误处理和事务；便于测试。
- 代价：初期文件数量多于直接 CRUD。

## D-010 默认不引入大型全局状态库

- 状态：Accepted
- 日期：2026-08-11
- 背景：MVP 的持久状态已有 IndexedDB，重复建立全局业务状态容易出现双数据源。
- 决策：数据库作为持久事实来源；表单和 UI 临时状态使用 React 本地状态/Context。
- 理由：减少依赖和同步问题。
- 后续触发：出现无法通过局部状态和查询解决的跨页面临时状态时，再评估状态库。

## D-011 Upcoming 先采用七天列表

- 状态：Accepted
- 日期：2026-08-11
- 背景：日历网格、拖拽排期和外部日历同步会扩大 UI 和日期处理范围。
- 决策：MVP 提供明日起未来七天的分组列表。
- 理由：足以支持短期计划和过载观察；实现可控。
- 代价：缺少月度全局视野和时间块安排。

## D-012 MVP 不建设后端

- 状态：Accepted
- 日期：2026-08-11
- 背景：账号、鉴权、API、数据库、备份、同步和冲突解决会把个人 MVP 变成完整 SaaS。
- 决策：MVP 静态部署，不包含任务 API 或云数据库。
- 理由：优先验证用户是否愿意持续使用产品模型。
- 代价：无多设备同步和远程备份。
- 后续触发：跨设备成为高频刚需时，单独形成同步架构文档和隐私模型。

## D-013 用重要性与紧急性两轴替代单一优先级

- 状态：Accepted
- 日期：2026-08-11
- 背景：用户希望给任务赋予“重要”“紧急”“不重要”“不紧急”标识并筛选。把四个词做成普通标签会允许互相矛盾的组合；同时保留 `low/medium/high` 优先级又会形成两套重叠判断。
- 决策：移除 MVP 的单一 `priority` 字段，改为可空的 `importance` 和 `urgency` 两个互斥维度；四象限由两者派生。
- 理由：既能单独筛选所有重要或紧急任务，也能精确筛选四个象限，并在快速创建时保留“未分类”。
- 代价：筛选 UI 和导入校验增加两个字段；旧的“优先级排序”改为“四象限排序”。
- 被拒绝方案：把四个词写入普通 `tagIds`；同时保留单一优先级；创建时强制选择两个维度。
- 后续触发：真实使用证明需要独立矩阵操作时，再增加四象限页面；MVP 只做分类标识、筛选和排序。
